# 06 - DevSecOps Culture

## Overview

DevSecOps is not only about security tools.

A successful DevSecOps culture requires:

    Autonomy
    Visibility
    Transparency
    Understanding
    Empathy
    Trust

---

## Promote Autonomy of Teams

Security must scale with the organisation.

Security teams cannot be present in every development conversation.

Therefore, teams should be able to make secure decisions independently.

This can be achieved through:

    Automation
    Playbooks
    Runbooks
    Education
    Integrated Security Tests

Security tests should become another normal type of development test.

---

## Playbooks and Runbooks

Teams can use playbooks and runbooks to understand:

    How to Identify Security Flaws
    How to Fix Them
    What Their Risk Is
    What Actions Should Be Taken

This increases confidence and reduces dependence on a central security team.

---

## Visibility and Transparency

Teams need visibility into the security state of the services they own.

For example:

    Security Dashboard
          ↓
    Findings
          ↓
    Severity
          ↓
    Prioritisation

This helps prevent important security findings from getting lost in backlog noise.

---

## Transparent Security Tools

Security tools should provide useful information directly to developers.

For example:

    Code Check
        ↓
    Security Finding
        ↓
    Affected Line
        ↓
    Explanation
        ↓
    Remediation Guidance

Giving development teams access to this information promotes:

    Education
    Autonomy
    Trust

---

## Understanding and Empathy

Different teams can have different definitions of risk.

Security teams may prioritise a potential vulnerability differently from the team responsible for a critical service.

Therefore, DevSecOps processes should consider:

    Team Priorities
    Deadlines
    Available Resources
    Service Importance
    Actual Exploitability
    Business Context

---

## No One-Size-Fits-All Process

There is no single security tool or process that works perfectly for every team.

Security processes should be flexible enough to adapt to:

    Different Teams
    Different Services
    Different Risks
    Different Deadlines
    Different Resources

Understanding how a team works makes it easier to build a process they will actually use.

---

## Building Trust

A security team should avoid continuously reporting low-value findings that create noise.

Instead:

    Understand Context
        ↓
    Prioritise Correctly
        ↓
    Reduce Noise
        ↓
    Demonstrate Value
        ↓
    Build Trust

---

## Key Takeaways

- Promote autonomy so security can scale.
- Use automation to integrate security into development.
- Playbooks and runbooks help teams make secure decisions.
- Visibility allows teams to understand their security state.
- Transparency gives developers access to useful security information.
- Understanding and empathy help security processes fit real development environments.
- Trust is essential for successful DevSecOps culture.
